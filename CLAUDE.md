## What this is

Jarvis is Bassam's personal learning project: a personal AI assistant built incrementally across milestones (text chat -> voice -> persistent memory -> vision + PC control -> coding ability). The point of the project is for Bassam to grow as a Python developer, not to ship Jarvis quickly. Stays on Claude's API throughout — a local-LLM milestone was considered and explicitly dropped (2026-07-05): the only motivation was cost savings, and for a personal single-user assistant the API cost isn't a real problem worth the reliability hit and infra work of self-hosting.

Milestones 1 (terminal text chat), 2 (voice, in/out both working), 3 (persistent memory — closed as MVP: write + full-file read-back work; topic classification and index-based lookup deferred, see `teacher/MILESTONE3_PROGRESS.md`), and 4 (filesystem/shell control — closed 2026-07-10: Jarvis delegates real system tasks from the always-on Haiku conversation to a Sonnet 5 task executor via a `delegate_task` tool, which runs PowerShell commands through a `run_command`-style tool-use loop and reports the result back in Haiku's own voice) are complete. Currently on Milestone 5 (vision + PC control — this was M4's original scope before Bassam split filesystem/shell control out to be built first on 2026-07-06). Coding ability is the planned milestone after that; whether Jarvis gets a frontend or stays background-only is an open decision to make once M5 is built.

## Operating mode for this repo: teach, don't build

Bassam is an intermediate Python developer and wants a mentor, not a developer who writes code for him. This overrides default "just implement it" behavior:

- Never paste complete, ready-to-run solutions. Give skeletons, hints, or isolated single-concept examples, and have him write/adapt the rest.
- Ask what he thinks should happen before explaining or fixing.
- If his code has a bug, ask him to spot it before revealing it.
- Never agree just to be agreeable. If an approach will cause problems, say so plainly and explain why — even if he says to just do it his way (give one honest warning, then respect the choice).
- Bassam explicitly wants to be evaluated against senior-SWE judgment, not just told he's right. When he proposes a design or names a mindset/principle, actively check whether it actually holds up (right tool for the job size, sequencing, common pitfalls) and correct him plainly when it doesn't — even on small choices like "is this the right mindset."
- Walk through milestones one at a time; check his plan/reasoning before jumping into implementation for the next step.

## Code in this repo

- `Jarvis_Talking.py` — the real entry point. `main()` builds a SAPI speaker (`win32com.client.Dispatch("SAPI.SpVoice")`) and a `speech_recognition` recognizer/mic, calibrates ambient noise once before the loop, then runs a `while True` chat loop: `listener(recognizer, mic)` records from the mic and transcribes with local Whisper, an empty-transcription guard skips to the next loop iteration if Whisper returns `''`, then it appends a user dict to `history`, calls `get_jarvis_response(history, voice)`, appends the returned reply as an assistant dict, prints it, and speaks it via `voice.Speak(response)`. `get_jarvis_response` loads `.env`, builds the `anthropic.Anthropic` client, reads `jarvis_personality.txt` into a `system` prompt, and calls `client.messages.create(...)` on `claude-haiku-4-5` with `tools=[DELEGATE_TASK_TOOL]` and `messages=history`. If the response contains a `tool_use` block for `delegate_task` (not a text-match trigger — genuine tool-use, added after the earlier text-match approach proved unreliable, see git history around `jarvis_can_now_cmd`), any filler text blocks are spoken immediately via `voice.Speak`, the task string is handed to `jarvis_command()` in `jarvis_cmd.py`, the result is injected into `history` as a `[Task result]`-tagged user message, and Haiku is called a second time so it reports the outcome in its own voice. Otherwise the plain-text response is returned directly. See [teacher/MILESTONE2_PROGRESS.md](teacher/MILESTONE2_PROGRESS.md) for known issues (Whisper model reloads every call) and what's left.
- `jarvis_cmd.py` — Milestone 4's task-execution arm. `jarvis_command(user_command)` runs a `while True` tool-use loop against `claude-sonnet-5` (system prompt from `jarvis_tasking.txt`, bound to `RUN_COMMAND_TOOL`): each iteration appends the assistant's turn to its own local `messages` list, checks for a `command_tool` tool-use block, runs it via `command_tool()` (`subprocess.run(["powershell", "-Command", command], cwd=working_directory, ...)`, no timeout, no call cap — both intentionally left out per Bassam's "let it run, I don't care" call), and appends a `tool_result`; once a response has no tool_use, that plain text is the final answer, returned as `{"role": "assistant", "content": text}`. No separate action-log memory — Bassam decided Haiku's own conversation history already carries enough context, so the earlier `Memory` class (a `Jarvis_Commands.md` log) was removed.
- `Jarvis_Memory.py` — persistent memory (Milestone 3). `write_to_memory(user_text, jarvis_text)` appends both sides of each turn as labeled lines (`Engineer Bassam:` / `Jarvis_Response:`) to `C:\Users\kitan\Documents\Obsidian Vault\jarvis_memory\Jarvis_Chat.md`. `read_to_memory()` reads that file and `text_to_dict()` parses it back into `{"role", "content"}` dicts, stripping the labels from content; any line that doesn't start with a known label gets appended onto the previous entry's content instead of being dropped, so multi-line responses survive the round trip. `Jarvis_Talking.py` calls `history = Jarvis_Memory.read_to_memory()` at startup and `write_to_memory(...)` after each turn. Whole file is replayed into context every run — accepted MVP limitation, smart lookup deferred.
- `jarvis_personality.txt` — plain-text system prompt defining Jarvis's identity, tone, and hard constraints (no emojis, respect the hierarchy with Bassam, etc.). Tells Jarvis he has a voice and to avoid formatting that doesn't survive being spoken. Also covers: when to use `delegate_task` (never describe doing filesystem/system work yourself), the hard rule that it has zero real-world effect without a `[Task result]` actually landing in the conversation (added after Haiku was observed hallucinating "done" responses without calling the tool), how to react to `[Task result]`-tagged messages, and a no-repeating-the-last-reply's-opening-line rule. Read fresh on every call inside `get_jarvis_response` — known minor inefficiency, not yet worth fixing.
- `jarvis_tasking.txt` — Sonnet's system prompt for `jarvis_command()`, sibling to `jarvis_personality.txt`. Defines the task-executor persona, PowerShell usage, the `working_directory`-must-be-passed-every-call caveat (each `command_tool` call is a fresh process, no `cd` persistence), and the rule that its final answer must be plain, spoken-friendly language, not a technical command log.
- `jarvis_EMK.py` — Milestone 5's screen-vision-and-control arm, in progress. `COMPUTER_TOOL` declares Anthropic's official `computer_20251124` tool (schema-less, requires `betas=["computer-use-2025-11-24"]` on `client.beta.messages.create`). `jarvis_screen_action(user_command)` mirrors `jarvis_cmd.py`'s loop shape exactly (call model, append assistant turn, detect `tool_use`, execute, append `tool_result`, loop; no call cap, same as M4). `handle_computer_action(input)` dispatches all 11 possible actions (`screenshot`, `left_click`, `type`, `key`, `scroll`, `right_click`, `double_click`, `mouse_move`, `hold_key`, `wait`, `zoom`) to matching handler functions — **every handler is still `raise NotImplementedError`**, nothing can see or touch the screen yet. Display dims are computed from Bassam's real two-monitor virtual desktop (queried via `System.Windows.Forms.Screen.AllScreens`, not guessed): primary 2560x1080 at (0,0), secondary portrait 1080x1920 at (2560,-534), combined 3640x1920 downscaled to 2576x1359 to fit Sonnet 5's resolution cap. See [teacher/MILESTONE5.md](teacher/MILESTONE5.md) for the full current state and what's next.
- `jarvis_screen_personality.txt` — Sonnet's system prompt for `jarvis_screen_action()`, sibling to `jarvis_tasking.txt`. Tells it the monitor layout so it can read combined screenshots correctly, and — unlike `jarvis_tasking.txt`'s "keep it short" rule — instructs maximally detailed, expressive final answers (framed as audio description for a blind listener) since neither Haiku nor Bassam ever see the screenshots; Sonnet's text is the only channel that information travels through. Also explicitly lists which actions actually have working code paths vs. which don't, so it doesn't call something unimplemented and assume it worked.
