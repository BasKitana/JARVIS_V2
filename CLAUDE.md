## Code in this repo

- `Jarvis.py` (renamed from `Jarvis_Talking.py`) — the real entry point. `main()` builds a SAPI speaker (`win32com.client.Dispatch("SAPI.SpVoice")`) and a `speech_recognition` recognizer/mic, calibrates ambient noise once before the loop, then runs a `while True` chat loop: `listener(recognizer, mic)` records from the mic and transcribes with local Whisper, an empty-transcription guard skips to the next loop iteration if Whisper returns `''`, then it appends a user dict to `history`, calls `get_jarvis_response(history, voice)`, appends the returned reply as an assistant dict, prints it, and speaks it via `voice.Speak(response)`. `get_jarvis_response` loads `.env`, builds the `anthropic.Anthropic` client, reads `system_prompts/jarvis_personality.txt` into a `system` prompt, and runs its own `while True` tool-use loop on `claude-haiku-4-5` with `tools=[DELEGATE_TASK_TOOL, DELEGATE_SCREEN_TOOL, MEDIA_CONTROL_TOOL]` and `messages=history` — this replaced the earlier single-shot-then-one-retry design (2026-07-15) so Jarvis can chain multiple delegated actions across one user turn instead of being capped at one. Each iteration: if the response has no `tool_use` block, its text is the final answer, returned directly. If it does, any text blocks are spoken immediately via `voice.Speak`, the model's own turn (`response.content`, tool_use block included) is appended to `history` as a real assistant turn, the task string is dispatched to `jarvis_command()` (`delegate_task`), `jarvis_screen_action()` (`delegate_screen_task`), or `jarvis_media()` (`media_control`), and the result comes back as a proper `{"type": "tool_result", "tool_use_id": ...}` block appended as the next user turn — not the earlier `[Task result]`-tagged plain-text hack, which never stored the model's own tool_use turn and couldn't support more than one hop. The loop then calls the model again. See [teacher/MILESTONE2_PROGRESS.md](teacher/MILESTONE2_PROGRESS.md) for known issues (Whisper model reloads every call) and what's left.
- `jarvis_cmd.py` — Milestone 4's task-execution arm. `jarvis_command(user_command)` runs a `while True` tool-use loop against `claude-sonnet-4-6` (`output_config={"effort": "low"}`, system prompt from `system_prompts/jarvis_tasking.txt`, bound to `RUN_COMMAND_TOOL`): each iteration appends the assistant's turn to its own local `messages` list, checks for a `command_tool` tool-use block, runs it via `command_tool()` (`subprocess.run(["powershell", "-Command", command], cwd=working_directory, ...)`, no timeout, no call cap — both intentionally left out per Bassam's "let it run, I don't care" call), and appends a `tool_result`; once a response has no tool_use, that plain text is the final answer, returned as `{"role": "assistant", "content": text}`. No separate action-log memory — Bassam decided Haiku's own conversation history already carries enough context, so the earlier `Memory` class (a `Jarvis_Commands.md` log) was removed.
- `Jarvis_media.py` — the interim Spotify/YouTube media-control arm (started 2026-07-15, no dedicated milestone — see `teacher/MILESTONE5.md`'s "Interim detour" section). No LLM inside it at all — by design, since Spotify/YouTube actions are a small, deterministic action set, not open-ended tasks needing a reasoning sub-loop like `jarvis_command`/`jarvis_screen_action`. `_spotify_token()`/`_spotify_device()`/`_spotify_ensure_device()`/`_spotify_transfer()`/`_spotify_request()`/`_spotify_start()`/`_spotify_control()` are raw `httpx` calls against the Spotify Web API (no `spotipy` dependency), ported near-verbatim from the older `jarvis` repo (`BasKitana/jarvis`) — refresh-token OAuth flow (`SPOTIFY_CLIENT_ID`/`SPOTIFY_CLIENT_SECRET`/`SPOTIFY_REFRESH_TOKEN` in `.env`, refresh token minted once via a one-time authorization script that was deleted after use), retry-with-device-wake logic for the classic "device asleep" 404/502 flakiness. `handle_spotify(user_input, t)` is the regex/keyword dispatcher (skip/pause/resume, liked songs, playlist search-by-name-or-genre, specific song search with "song by artist" parsing) — also ported from the old repo essentially unchanged, since that's exactly the "identify what specifically to do" layer the design wanted reused. `youtube_action(user_input, t)` needs no auth at all — scrapes the YouTube search-results page for the first `videoId` and opens it via `webbrowser.open()`. `jarvis_media(user_command)` is the new entry point tying it to the tool-use architecture: pulls the task text, lowercases it, routes to `youtube_action` or `handle_spotify` (Spotify is the default per the personality prompt's existing preference), returns `{"role": "assistant", "content": result}` — same shape `jarvis_command`/`jarvis_screen_action` return.
- `Jarvis_Memory.py` — persistent memory (Milestone 3). `write_to_memory(user_text, jarvis_text)` appends both sides of each turn as labeled lines (`Engineer:` / `Jarvis_Response:`) to `C:\Users\kitan\Documents\Obsidian Vault\jarvis_memory\Jarvis_Chat.md`. `read_to_memory()` reads that file and `text_to_dict()` parses it back into `{"role", "content"}` dicts, stripping the labels from content; any line that doesn't start with a known label gets appended onto the previous entry's content instead of being dropped, so multi-line responses survive the round trip. `memory_clerk()` runs the raw chat log through `claude-haiku-4-5` (system prompt `system_prompts/clerk_prompt.txt`) to distill it into `Jarvis_Mind.md` and clear `Jarvis_Chat.md`. `Jarvis.py` calls `history = Jarvis_Memory.read_to_memory()` at startup and `write_to_memory(...)` + `memory_clerk()` after each turn. Whole file is replayed into context every run — accepted MVP limitation, smart lookup deferred.
- `system_prompts/jarvis_personality.txt` — plain-text system prompt defining Jarvis's identity, tone, and hard constraints (no emojis, respect the hierarchy with the Engineer, etc.). Tells Jarvis he has a voice and to avoid formatting that doesn't survive being spoken. Also covers: which of the three delegation tools (`delegate_task`, `delegate_screen_task`, `media_control`) matches a given request — including the rule that Spotify/YouTube requests (even a bare "open Spotify") go to `media_control`, not `delegate_task`, since that subsystem already handles checking whether the app/device is active and launching it if not; the hard rule that nothing has zero real-world effect without an actual `[Task result]` landing in the conversation (added after Haiku was observed hallucinating "done" responses without calling a tool); and a no-repeating-the-last-reply's-opening-line rule. Read fresh on every call inside `get_jarvis_response` — known minor inefficiency, not yet worth fixing.
- `system_prompts/jarvis_tasking.txt` — Sonnet's system prompt for `jarvis_command()`, sibling to `jarvis_personality.txt`. Defines the task-executor persona, PowerShell usage, the `working_directory`-must-be-passed-every-call caveat (each `command_tool` call is a fresh process, no `cd` persistence), and the rule that its final answer must be plain, spoken-friendly language, not a technical command log.
- `jarvis_EMK.py` — Milestone 5's screen-vision-and-control arm, in progress. `COMPUTER_TOOL` declares Anthropic's official `computer_20251124` tool (schema-less, requires `betas=["computer-use-2025-11-24"]` on `client.beta.messages.create`). `jarvis_screen_action(user_command)` mirrors `jarvis_cmd.py`'s loop shape exactly (call model, append assistant turn, detect `tool_use`, execute, append `tool_result`, loop; no call cap, same as M4), against `claude-sonnet-4-6` with `output_config={"effort": "low"}`. `handle_computer_action(input)` dispatches all 11 possible actions (`screenshot`, `left_click`, `type`, `key`, `scroll`, `right_click`, `double_click`, `mouse_move`, `hold_key`, `wait`, `zoom`) to matching handler functions — **every handler is still `raise NotImplementedError`**, nothing can see or touch the screen yet. Display dims are computed from Bassam's real two-monitor virtual desktop (queried via `System.Windows.Forms.Screen.AllScreens`, not guessed): primary 2560x1080 at (0,0), secondary portrait 1080x1920 at (2560,-534), combined 3640x1920 downscaled to 2576x1359 to fit the model's resolution cap. See [teacher/MILESTONE5.md](teacher/MILESTONE5.md) for the full current state and what's next.
- `system_prompts/jarvis_screen_personality.txt` — Sonnet's system prompt for `jarvis_screen_action()`, sibling to `jarvis_tasking.txt`. Tells it the monitor layout so it can read combined screenshots correctly, and — unlike `jarvis_tasking.txt`'s "keep it short" rule — instructs maximally detailed, expressive final answers (framed as audio description for a blind listener) since neither Haiku nor Bassam ever see the screenshots; Sonnet's text is the only channel that information travels through. Also explicitly lists which actions actually have working code paths vs. which don't, so it doesn't call something unimplemented and assume it worked.
